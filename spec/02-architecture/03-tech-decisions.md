# 关键技术决策

## 为什么选择 Python 而非 Node.js

**异步生态成熟度**
Python 的 asyncio 生态经过多年发展，拥有 FastAPI、httpx、aiofiles 等成熟的异步库。类型注解系统（type hints）在 Python 3.11+ 中已经非常完善。

**LLM SDK 支持**
OpenAI、Anthropic 等厂商优先提供 Python SDK，功能更新更快。虽然 Node.js 也有 SDK，但 Python 在 AI/ML 领域的生态更加丰富。

**浏览器自动化**
Playwright 的 Python 版本与 Node.js 版本功能对等，可以无缝替代 Puppeteer。

**进程隔离执行**
Python 的 multiprocessing 和 subprocess 模块提供了完善的进程管理能力，适合实现安全的代码沙箱。

## 全异步架构

系统采用全异步架构，所有 I/O 操作（文件、网络、数据库）都使用 async/await。这种设计的优势：

- **高并发**：单线程可以处理大量并发连接，适合 HTTP API 服务
- **资源效率**：避免线程切换开销，内存占用更低
- **代码清晰**：异步代码比回调或线程更易于理解和维护

需要注意的问题：
- 避免在异步代码中调用阻塞操作
- CPU 密集型任务需要放到线程池或进程池
- 异常处理需要使用 try/except，不能用回调

## 配置服务设计哲学

配置服务采用"通用、无感知"的设计哲学：

**为什么不为每个配置项提供专用方法？**

如果为 LLM 配置提供 `get_llm()`、为工作空间配置提供 `get_workspaces()`，配置服务就与业务逻辑深度耦合。每次新增模块都需要修改配置服务，违反了开闭原则。

**通用设计的优势**
- 配置服务只关注"如何存储和读取"，不关心"存储什么"
- 各模块自行定义配置结构和验证逻辑
- 新增模块无需修改配置服务
- 配置服务可以用在其他项目中

**配置覆盖机制**
基础配置存储在 `app.json`，本地覆盖存储在 `app.local.json`。后加载的覆盖前者。这种设计允许：
- 版本控制提交默认配置
- 敏感信息（API Key）放在 .local.json 不提交
- 用户自定义配置不冲突

## 工具系统设计

工具系统采用"注册-发现-执行"模式：

**工具注册**
系统启动时，各模块向 ToolExecutor 注册工具。注册时提供：
- 工具名称
- 工具描述
- 参数定义（JSON Schema）
- 处理函数

**工具发现**
当智能体需要工具时，RuntimeTools 根据智能体的岗位配置，返回允许的工具列表。这个列表会被格式化为 OpenAI function calling 格式。

**工具执行**
LLM 返回 tool_calls 后，RuntimeTools 验证权限，调用 ToolExecutor 执行。执行时传递 ToolContext，包含 runtime 引用、agent_id、task_id 等上下文。

**为什么需要 ToolGroup？**
工具组（ToolGroup）是对工具的归类。岗位配置使用工具组而非单个工具，因为：
- 简化配置：配置 "workspace" 工具组比列出 5 个文件操作工具更简单
- 权限控制：可以整体启用/禁用某类工具
- 扩展性：新增工具添加到现有组，无需修改岗位配置

## 消息总线设计

消息总线采用"队列+延迟堆"的设计：

**即时消息队列**
每个智能体有一个消息队列（List）。消息到达时直接加入队列，如果智能体空闲，立即触发处理。

**延迟消息堆**
延迟消息存储在最小堆中，按投递时间排序。后台任务定期检查堆顶，到达时间的消息移入对应智能体的即时队列。

**插话（Interruption）机制**

插话是系统的核心特性，允许在智能体等待 LLM 响应时接收新消息，并将新消息合并到对话上下文中处理。

**使用场景**：用户发送指令后补充信息、其他智能体发送紧急消息、用户改变主意需要修改请求。

**触发条件**：目标智能体状态为 `waiting_llm` + 新消息是即时消息（非延迟消息）。

**核心机制**：
- **AgentCancelManager**：为每个智能体维护 epoch（世代号），插话时递增 epoch
- **插话队列**：新消息被添加到 `_interruptionQueues`，而非替换当前处理
- **结果丢弃**：LLM 响应返回时对比 epoch，若已过期则丢弃结果
- **上下文合并**：TurnEngine 在调用 LLM 前将插话消息合并到对话上下文

**处理流程**：
1. MessageBus.send() 检测到目标正在 waiting_llm，触发 onInterruptionNeeded
2. RuntimeMessaging 将新消息添加到插话队列
3. AgentCancelManager.abort() 递增 epoch
4. 当前 LLM 调用返回，ComputeScheduler 检查到 epoch 不匹配，丢弃结果
5. TurnEngine 在 need_llm 阶段获取插话消息，合并到上下文
6. 基于包含插话的上下文重新调用 LLM

**设计考虑**：
- HTTP 请求难以真正取消，服务器仍在处理
- 将插话合并到上下文比取消重试更符合对话连贯性
- epoch 机制可以区分多次连续插话，追踪时间顺序

详见 [核心层设计 - 插话机制](03-core-layer.md#3-插话interruption机制)

## 智能体记忆设计

**为什么需要长期记忆？**

对话历史有长度限制，无法保留所有过往信息。智能体需要长期记忆来：
- 记住用户的偏好和习惯
- 记录重要的项目信息
- 在长时间对话后仍能引用早期内容

**记忆系统架构**

- **AgentMemoryManager**：管理所有智能体的记忆实例，每个智能体完全隔离
- **向量存储**：使用 SQLite + 向量索引，基于 Embedding 进行相似度检索
- **自动提取**：累积 10 条消息时自动触发记忆提取
- **上下文注入**：调用 LLM 前自动检索相关记忆，注入到 system prompt

**记忆流程**

```
对话消息 -> 累积10条 -> 提取记忆 -> 生成向量 -> 存储
                                              ↓
用户提问 -> 检索相关记忆 -> 注入上下文 -> 调用 LLM
```

**设计考虑**

- 记忆按智能体隔离，保护隐私
- 支持本地 Embedding 服务（LLM-Modules）或远程 API
- 记忆系统故障不影响主流程

详见 [服务层设计 - 智能体记忆服务](04-service-layer.md#8-agent-memory-service-智能体记忆服务)
