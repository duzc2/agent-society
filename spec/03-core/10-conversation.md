# Conversation Manager 对话管理

## 1. 职责

ConversationManager 负责管理智能体与 LLM 的对话历史：
- 存储和查询对话记录
- 构建 LLM 上下文（system + history）
- 自动压缩和裁剪（可选）
- 持久化到文件

## 2. 对话记录格式

对话记录存储为 OpenAI message 格式：

消息角色：
- system：系统提示词
- user：用户输入（包括插话消息）
- assistant：助手回复
- tool：工具执行结果

每条消息包含：
- role：消息角色
- content：消息内容（字符串或数组）
- name：工具名称（仅 tool 角色）
- tool_call_id：工具调用ID（仅 tool 角色）

示例对话记录：
```json
[
  { "role": "system", "content": "You are a helpful assistant." },
  { "role": "user", "content": "Hello" },
  { "role": "assistant", "content": "Hi there!" }
]
```

## 3. 上下文构建流程

### 3.1 完整流程

构建 LLM 上下文时执行以下步骤：

1. **获取系统提示词**
   - 从智能体配置获取基础 system prompt
   - 可能包含动态生成的内容（如相关记忆）
   - 作为消息列表的第一条

2. **加载对话历史**
   - 从内存缓存或文件加载历史消息
   - 按时间顺序排列
   - 排除已删除或无效的消息

3. **合并插话消息**
   - 如果有插话消息，格式化为用户消息
   - 在内容前添加标记【插话消息】
   - 插入到历史末尾、当前消息之前

4. **追加当前消息**
   - 将当前需要处理的消息添加到末尾
   - 如果是工具调用结果，使用 tool 角色
   - 如果是用户输入，使用 user 角色

5. **Token 检查与压缩**
   - 估算消息列表的 token 数量
   - 如果超过阈值，触发压缩
   - 保留 system 消息不被压缩

6. **返回消息列表**
   - 返回完整的 OpenAI 格式消息列表
   - 可以直接传递给 LLM API

### 3.2 插话消息处理

在 TurnEngine 的 need_llm 阶段处理插话：

获取插话消息：
- 调用 get_and_clear_interruptions(agent_id)
- 获取并清空该智能体的插话队列
- 返回消息列表

格式化插话消息：
- 如果有多条插话，合并为一条消息
- 在内容开头添加标记：【插话消息】\n
内容格式：
```
【插话消息】
[第一条插话内容]
[第二条插话内容]
...
```

消息角色设置为 user，表示来自用户的打断。

插入位置：
- 在对话历史之后
- 在当前待处理消息之前
- 让 LLM 感知到这是中断

## 4. 持久化策略

### 4.1 即时持久化

每次消息追加后立即保存：
- 确保系统崩溃后不会丢失对话
- 使用异步写入不阻塞主流程
- 写入失败记录错误但不中断

### 4.2 文件格式

每个智能体一个独立的 JSON 文件：
- 存储位置：conversations/{agent_id}.json
- 格式：JSON 数组，每条消息一个对象
- 编码：UTF-8

文件结构：
```json
{
  "agent_id": "agent-xxx",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "...", "usage": {...}}
  ],
  "created_at": "2024-01-01T00:00:00Z",
  "updated_at": "2024-01-01T00:00:00Z"
}
```

### 4.3 加载流程

系统启动或首次访问时加载对话：

1. 检查文件是否存在
2. 如果存在，读取并解析 JSON
3. 验证数据格式
4. 加载到内存缓存
5. 如果文件不存在，创建新的空对话

### 4.4 保存流程

追加消息后触发保存：

1. 将对话对象转为 JSON 字符串
2. 使用原子写入（先写临时文件再重命名）
3. 更新 updated_at 时间戳
4. 异步执行不阻塞

## 5. 对话压缩（可选）

### 5.1 触发条件

当对话 token 数超过阈值时触发压缩：
- 默认阈值：4000 tokens
- 在构建上下文时检查
- 只压缩历史，保留当前消息

### 5.2 压缩策略

**滑动窗口模式**

只保留最近 N 条消息：
- 删除早期消息
- 保留 system 消息
- 简单高效，但丢失历史上下文

**摘要模式**

将早期对话压缩为摘要：
- 保留最近 10 条完整消息
- 使用 LLM 生成前面内容的摘要
- 将摘要作为 system 消息插入
- 平衡上下文长度和信息保留

**智能选择模式**

使用 LLM 选择最重要的消息：
- 评估每条消息的重要性
- 保留关键决策和问题
- 删除重复或冗余内容
- 需要额外的 LLM 调用

### 5.3 压缩实现

压缩流程：

1. 估算当前 token 数
2. 如果超过阈值：
   - 确定要压缩的消息范围
   - 调用压缩策略（滑动窗口/摘要/智能选择）
   - 生成压缩后的消息列表
   - 替换原对话历史
3. 更新持久化文件

Token 估算：
- 使用 tiktoken 库（OpenAI 官方）
- 根据模型选择对应的编码器
- 快速估算，不需要精确值

## 6. 内存管理

### 6.1 缓存策略

对话数据在内存中缓存：
- 使用映射表存储，agent_id 为键
- 最近使用的对话保留在内存
- 长时间未使用的可以释放（LRU策略）

### 6.2 加载时机

- 智能体首次发送消息时加载
- 系统启动时恢复活跃的对话
- 按需加载，避免占用过多内存

### 6.3 数据一致性

- 内存中的数据是主要副本
- 文件是持久化备份
- 定期或在关键操作时同步

## 7. 接口说明

### 7.1 加载对话

输入：
- agent_id：智能体ID

处理：
- 检查内存缓存
- 如果未加载，从文件读取
- 如果文件不存在，创建新对话

输出：
- 对话对象（包含消息列表）

### 7.2 保存对话

输入：
- agent_id：智能体ID

处理：
- 获取内存中的对话
- 序列化为 JSON
- 原子写入文件

输出：
- 成功/失败状态

### 7.3 追加消息

输入：
- agent_id：智能体ID
- message：消息对象（role, content 等）

处理：
- 确保对话已加载
- 追加消息到消息列表
- 更新 updated_at
- 触发持久化

输出：
- 成功/失败状态

### 7.4 构建上下文

输入：
- agent_id：智能体ID
- system_prompt：系统提示词
- current_message：当前消息
- interruptions：插话消息（可选）

处理：
- 构建消息列表
- 检查 token 数并压缩
- 返回完整上下文

输出：
- 消息列表（OpenAI 格式）

## 8. 使用场景

### 8.1 智能体处理消息

当智能体收到新消息时：
1. 加载或获取对话
2. 构建上下文（包含历史和插话）
3. 调用 LLM
4. 将 LLM 回复追加到对话
5. 保存对话

### 8.2 工具调用结果

当工具执行完成后：
1. 构建 tool 角色的消息
2. 追加到对话
3. 重新构建上下文
4. 再次调用 LLM

### 8.3 系统恢复

系统重启时：
1. 遍历所有智能体
2. 加载各自的对话文件
3. 恢复到内存缓存
4. 继续处理未完成的对话
