# 错误处理

## 1. 错误分类

### 1.1 系统错误

系统级错误，通常需要管理员干预：

- 配置文件损坏或丢失
- 磁盘空间不足
- 网络不可达
- 权限不足（文件系统）
- 依赖服务不可用

这类错误可能导致系统无法正常启动或运行。

### 1.2 运行时错误

运行过程中发生的错误，可以恢复或降级：

- 智能体不存在
- 工具调用失败
- LLM API 错误
- 消息格式无效
- 工作空间操作失败

这类错误通常返回给调用方，由上层决定如何处理。

### 1.3 用户错误

由用户操作引起的错误：

- 无效参数（缺少必填字段、类型错误）
- 权限不足（访问其他智能体的资源）
- 资源不存在（访问已删除的智能体）
- 格式错误（JSON 解析失败）

这类错误需要友好的错误提示，帮助用户纠正。

## 2. 错误处理原则

### 2.1 尽早失败

参数验证在函数入口完成：
- 检查必填参数是否存在
- 验证参数类型和格式
- 检查资源是否存在
- 检查权限

资源检查在使用前完成：
- 打开文件前检查路径
- 调用服务前检查连接
- 访问智能体前检查存在性

不要隐藏错误：
- 不吞掉异常
- 不返回模糊的 "内部错误"
- 提供具体的错误信息

### 2.2 优雅降级

非关键错误不影响系统运行：
- 单个智能体失败不影响其他智能体
- 工具调用失败返回错误让 LLM 处理
- 可选功能失败时禁用该功能

关键错误明确提示用户：
- 配置文件错误，提示检查配置
- LLM 服务不可用，提示检查网络
- 磁盘空间不足，提示清理空间

提供恢复建议：
- 错误信息包含可能的解决方案
- 记录详细的恢复步骤
- 提供文档链接

### 2.3 完整日志

所有错误记录到日志：
- 使用适当的日志级别（error/warning）
- 记录完整的错误信息
- 记录发生时间和上下文

包含上下文信息：
- agentId：涉及哪个智能体
- taskId：涉及哪个任务
- toolName：涉及哪个工具
- userId：涉及哪个用户

包含堆栈跟踪：
- 记录完整的异常堆栈
- 帮助定位问题源头
- 便于调试和修复

## 3. 异常传播

### 3.1 异步上下文

异步代码中使用异常处理捕获错误：

处理流程：
1. 使用 try-except 包裹可能出错的代码
2. 捕获特定的异常类型
3. 将底层异常转换为业务异常
4. 记录原始异常信息
5. 抛出友好的业务异常

异常转换示例：
- 文件不存在 → ToolExecutionError("文件不存在: /path")
- 网络超时 → LlmError("LLM API 超时")
- JSON 解析失败 → ValidationError("无效的 JSON 格式")

### 3.2 异常层次

定义清晰的异常继承关系：

基础异常：
- AgentSocietyError：所有业务异常的基类
- 包含共同的属性和方法

具体异常类型：
- AgentNotFoundError：智能体不存在
- ToolExecutionError：工具执行失败
- LlmError：LLM 调用失败
- LlmInterruptedError：LLM 调用被中断
- ValidationError：参数验证失败
- PermissionDeniedError：权限不足

中断异常的特殊处理：
- LlmInterruptedError 包含中断原因
- 包含 epoch_delta（世代差）
- 用于判断是否需要重试

## 4. 错误响应

### 4.1 API 错误响应格式

错误响应统一格式：
```json
{
  "error_code": "错误代码",
  "message": "人类可读的错误描述",
  "details": { "额外详情": "..." },
  "suggestion": "建议的解决方案"
}
```

错误代码规范：
- AGENT_NOT_FOUND：智能体不存在
- PERMISSION_DENIED：权限不足
- TOOL_EXECUTION_FAILED：工具执行失败
- LLM_API_ERROR：LLM API 错误
- INVALID_PARAMETERS：参数无效
- RATE_LIMITED：请求过于频繁

额外详情：
- 包含具体的字段名和错误
- 包含资源ID等上下文
- 帮助前端显示详细错误

### 4.2 工具错误处理

工具执行错误返回给 LLM：

工具结果格式：
```json
{
  "role": "tool",
  "tool_call_id": "call_xxx",
  "content": "{\"success\": false, \"error\": \"文件不存在: /path/to/file\"}"
}
```

LLM 决定如何处理：
- 重试工具调用（参数修正）
- 采用备选方案
- 向用户说明错误
- 请求用户介入

### 4.3 用户界面错误

向用户显示的错误：
- 简洁明了
- 不包含技术细节
- 提供解决建议

日志中记录的错误：
- 包含完整信息
- 包含堆栈跟踪
- 包含上下文数据

## 5. 恢复策略

### 5.1 LLM 调用重试

可重试的错误：
- 网络超时（临时问题）
- 速率限制（稍后重试）
- 服务暂时不可用

不可重试的错误：
- 认证失败（需要修改配置）
- 无效参数（需要修改代码）
- 内容过滤（不符合政策）

重试策略：
- 最大重试次数：默认3次
- 退避策略：指数退避（1s, 2s, 4s）
- 最大等待时间：30秒

### 5.2 状态恢复

系统崩溃后恢复流程：

1. 加载持久化状态
   - 读取 org.json 恢复组织关系
   - 读取 agent.json 恢复智能体
   - 读取 messages.ndjson 恢复消息队列

2. 重置处理状态
   - 将所有智能体状态设为 idle
   - 清空处理中标记
   - 重置取消状态

3. 重新调度消息
   - 遍历所有消息队列
   - 将非空队列提交给调度器
   - 恢复正常处理

### 5.3 降级策略

服务不可用时降级：
- LLM 服务不可用 → 使用备用服务
- Embedding 服务不可用 → 跳过记忆功能
- 工作空间不可用 → 禁用文件操作

功能降级：
- 关闭非核心功能
- 减少并发数
- 延长超时时间

## 6. 日志规范

### 6.1 错误日志内容

每条错误日志应包含：

基本信息：
- 时间戳（精确到毫秒）
- 日志级别（ERROR/WARNING）
- 错误消息

上下文信息：
- 涉及的实体ID（agent、task等）
- 操作类型（send_message、tool_call等）
- 用户ID（如有）

技术信息：
- 异常类型和消息
- 完整的堆栈跟踪
- 相关变量的值

### 6.2 日志示例

工具执行失败：
```
[2024-01-01 12:00:00.123] ERROR: 工具执行失败
  agent_id: agent-xxx
  tool_name: replace_file
  error: Permission denied: /path/to/file
  stacktrace: ...
```

LLM 调用失败：
```
[2024-01-01 12:00:01.456] ERROR: LLM API 错误
  agent_id: agent-yyy
  service_id: gpt-4o
  error: Rate limit exceeded
  retry_count: 3
```

### 6.3 敏感信息过滤

日志中不记录：
- API Key（用 *** 替换）
- 密码和令牌
- 个人隐私信息
- 大文件内容（只记录大小）

## 7. 监控和告警

### 7.1 错误率监控

监控指标：
- 单位时间错误数
- 错误率（错误数/总请求数）
- 按错误类型分类统计

告警阈值：
- 错误率超过 5% 触发警告
- 错误率超过 20% 触发严重告警
- 连续错误超过 10 次触发告警

### 7.2 关键错误告警

立即告警的错误：
- 系统启动失败
- 数据库连接失败
- LLM 服务完全不可用

通知方式：
- 日志记录
- 控制台输出
- 可选的 Webhook 通知
