# 三方异步通知机制（v3）：智能体 ⇄ 网页 ⇄ 服务器进程（进程消息协议）

> 日期：2026-08-31　|　状态：v3 定稿（v2 的 stdio 通信被用户否决——"标准 IO 只是通用性解决方案"）
> **v3 变化**：服务器进程与平台/智能体/网页的通信改为**独立 socket 通道上的结构化消息协议**（ProcMessageHub），stdin/stdout 保留给普通进程与日志。用户已确认：传输=独立 socket；范围=消息+事件（RPC 二期）；SDK=Node 版+协议文档。

---

## 一、术语定义

| 名称 | 定义 |
|---|---|
| **智能体** | LLM agent，平台内智能体运行时（bus 端点） |
| **网页** | 浏览器 UI（`web/v3`、模块面板 iframe）（心跳端点） |
| **服务器进程** | **智能体创建的、在服务端运行的逻辑**——经 `localcmd`（本机）或 `remote`（SSH）启动的常驻程序。v3 起**可选的**第三种消息端点：接入 ProcMessageHub 后与智能体/网页同构通信 |
| **平台** | agent-society Node 进程：宿主 + 消息中枢（MessageBus / HeartbeatBroker / ProcMessageHub） |

## 二、通道全景（v3 目标）

| 通道 | 方向 | 机制 | 状态 |
|---|---|---|---|
| 智能体 ⇄ 服务器进程 | 双向 | **ProcMessageHub（新）**：进程 `msg`→智能体（进会话）；智能体 `proc_send` 工具→进程 | 本方案 v3 |
| 服务器进程 → 网页 | 单向 | 进程 `event` → 心跳广播 `proc_event`（60s TTL） | 本方案 v3 |
| 网页 → 服务器进程 | 单向 | `POST /api/proc-messaging/...` 消息 API → hub → 进程 | 本方案 v3 |
| 智能体 ⇄ 网页 | A/B | `__notify`（A）+ `ui_page_notify`（B1）+ RPC 离线保活（B2） | 本方案（沿用 v2 设计） |
| 服务器进程（无协议） | 后备 | stdin/stdout + 事件推送 + 面板文本输出（**零改动保留**） | 已有 |

**RPC 二期**（协议信封预留 `id` 字段）：进程↔智能体/进程↔进程请求-应答；本期只做「消息+事件」语义。

## 三、协议设计（v3 核心）

### 3.1 信封（JSONL over TCP socket，UTF-8，一行一条）

```json
{"v":1, "id":"uuid", "type":"hello",      "token":"<spawn专属>", "name":"crawler", "agentId":"agent-1"}
{"v":1, "id":"uuid", "type":"welcome",    "procId":"proc-xxx", "as":"proc:crawler#agent-1"}
{"v":1, "id":"uuid", "type":"msg",        "to":"agent-1", "payload":{"text":"..."}}
{"v":1, "id":"uuid", "type":"msg",        "to":"proc:crawler#agent-1", "payload":{"text":"..."}}
{"v":1, "id":"uuid", "type":"event",      "event":"progress", "data":{"percent":42}}
{"v":1, "id":"uuid", "type":"error",      "message":"...", "details":{...}}
{"v":1, "id":"uuid", "type":"ping"}    {"v":1, "id":"uuid", "type":"pong"}
```

- 路由地址 `proc:<name>#<agentId>`：进程在消息空间的地址；`to` 缺省=归属智能体。
- RPC 预留：`rpc`/`rpc_result` 信封已含 `id`，二期加路由与超时匹配（本期不实现）。
- 连接语义：进程断开=离线；SDK 支持断线重连（backoff）并重新 `hello`；hub 侧清理注册。

### 3.2 ProcMessageHub（新组件）

**位置**：`src/platform/services/proc_messaging/proc_message_hub.js`（+ 路由文件）

**职责**：
1. **常驻 TCP server**（127.0.0.1，端口 `listen(0)` 随机，bootstrap 时启动，注册到 runtime）。
2. **握手与身份**：接收连接 → 等待首条 `hello` → 校验 `token` 是否匹配该 agent 的 spawn 记录（token 由 spawn 时生成，见 3.3）→ 注册 `proc:<name>#<agentId>` → 回 `welcome`。
3. **进程 → 平台**（inbound JSONL 解析）：
   - `msg` → `bus.send({ to, from: "proc:<name>#<agentId>", extras: { kind: "proc_msg", procName } })`（智能体经插话/新回合接收，formatter 呈现【进程消息】）
   - `event` → `heartbeatBroker.broadcast("proc_event", { procId, procName, event, data, agentId }, 60_000)`（网页接收，见 3.5）
   - `error` → 同 event 语义广播 + log.error
4. **平台 → 进程**（outbound 写 socket，JSONL）：
   - 网页消息：`POST /api/proc-messaging/send` → 查注册表 → 写 `msg`
   - 智能体消息：bus 订阅（`to` 形如 `proc:name#agentId` 或 `proc:name`）→ 写 `msg`（智能体侧工具 `proc_send` 封装）
5. **生命周期**：socket `close`/`error` → 注销注册表（进程退出事件已由 ProcessEventPusher 推送，不重复）；hub 关闭时全部断开。

**安全**：127.0.0.1 绑定 + spawn 专属 token（uuid，注入进程 env，仅当次 spawn 有效）。超出"本机用户授权"范畴的连接（无 token/错 token）→ 关闭并 log.warn。

### 3.3 spawn 接入（零配置启用）

- `localcmd_spawn`（及进程管理）不变；**每次 spawn 时平台生成 `SOCIETY_PROC_HUB_PORT`（hub 端口）与 `SOCIETY_PROC_TOKEN`（本 spawn 专属）注入进程环境**（`process_manager.js` spawn env 合成处）。
- 进程带 SDK（或手写协议）连上即生效；普通进程无 SDK 不连接，直接忽略 env——**智能体无需任何显式开关**。
- 智能体侧新工具 `proc_send`（`modules/localcmd/tools.js` 或 proc_messaging 工具组）：`{ processId|name, text/payload }` → hub → 进程 `msg`。

### 3.4 消息呈现（formatter）

- 智能体收到进程 `msg`：`runtime_llm.registerMessageFormatter` 注册 predicate `msg?.extras?.kind === "proc_msg"` → 格式 `【进程消息·<procName>】<payload.text>`（含 data 摘要，截断 500）。
- 网页收到 `proc_event`：前端（面板及 v3 主页可选）`window.addEventListener('agent-notify')` 同源处理或专用 `proc_event` 处理器（面板显示消息流，见 3.5）。

### 3.5 网页侧

- **面板（`modules/localcmd/web/panel.*` 扩展）**：
  - 进程列表区：`GET /api/proc-messaging/processes`（多包含协议状态：connected/plain）
  - 协议进程：显示**结构化消息流**（类型/方向/时间，来自 `proc_event` 心跳 + 初始列表），输入框发送 → `POST /api/proc-messaging/send`（`msg`，非 stdin）
  - 普通进程：保持 v2 设计（文本输出 offset 轮询 + stdin 输入按钮）
- **v3 主页**：`proc_event` 心跳消息在 `heartbeatService` 分发层预留处理器（本期只在面板消费；主页全局进程状态栏列为后续可选项，不过度设计）。

## 四、A/B 通道（网页 ⇄ 智能体）——沿用 v2 定稿（不变）

- **A 通道**：`__notify`（闭包注入、零全局）→ `POST /api/modules/ui_page/notify-agent` → `bus.send(extras.kind=page_notify)` → 插话/新回合 + 聊天持久化 + formatter【页面通知】。
- **B1**：`ui_page_notify` 工具（fire-and-forget）→ 心跳 `ui_command{type:notify}` → `CustomEvent('agent-notify')`。
- **B2**：HeartbeatBroker 在线感知（`markClientSeen`/`isClientOnline`/`onClientOnline`）+ UiCommandBroker 离线保活重投（5 分钟窗，智能体只感觉慢）。
- 详见 `三方异步通知机制-完整方案.md` v2 章节（A/B 段落原样保留）。

## 五、不做的事（范围）

1. RPC（rpc/rpc_result）——二期，信封已预留；本期消息+事件。
2. remote 进程的协议接入（协议/SDK 不动，后续经 SSH 转发复用；remote 智能体通道已有）。
3. WebSocket/SSE/长轮询（用户决策 2，全局不变）。
4. clientId 分端感知（B2 取舍记录不变）。
5. 多语言 SDK（本期 Node + 协议文档；Python 等按文档手写）。
6. stdin/stdout 既有链路（普通进程、`read_output`、事件推送）一律不动。

## 七、风险与回退

| 风险 | 应对 |
|---|---|
| 本机其他进程冒充 agent 的进程 | hub 校验 spawn 专属 token；无效连接关闭 + log.warn |
| 进程协议消息饥饿智能体上下文 | msg 进会话属于"对话消息"（用户决策 1 的同类语义），formatter 摘要截断 500 字符；`event` 不进会话（只进网页） |
| hub 端口被占 | `listen(0)` 随机端口，无固定端口冲突 |
| SDL 断线风暴 | SDK 指数退避重连（1s→2s→4s→max 30s），hub 对同一 token 并发连接只保留最新 |
| 协议进程误用（普通进程被误认为协议进程） | 无 hello 的连接不注册；注册表只记录握手成功的进程 |
| 现有 localcmd/remote 测试回归 | spawn env 注入为纯增量（普通进程 env 多了两个变量，无行为变化） |
