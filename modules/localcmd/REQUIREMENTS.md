# localcmd 命令审核需求文档

## 1. 背景

`localcmd` 模块允许 AI 智能体在本地执行系统命令。当前没有任何审核机制，所有命令由 AI 直接执行。需要增加审核机制，让用户控制哪些命令可以执行。

## 2. 作用域

审核策略（黑白名单）归属于组织。组织间的策略相互独立，一个组织的策略不影响另一个组织。组织被删除时，其策略随之清除。

策略对组织下的所有智能体统一生效。

## 3. 命令规范化

在比对黑白名单之前，将原始命令转换为规范化形式。

### 3.1 第一个 token（可执行文件）

1. 取完整命令的第一个部分（到第一个空格为止）
2. 去掉路径前缀，取 basename
3. 去掉平台可执行后缀（`.exe`、`.bat`、`.cmd`、`.ps1`）

示例：

| 原始命令 | 规范化第一个 token |
|---|---|
| `C:\tools\python.exe train.py --epochs 10` | `python` |
| `./python /home/user/train.py` | `python` |
| `/usr/bin/python3 script.py` | `python3` |
| `.\some.exe --help` | `some` |
| `some.exe --help` | `some` |
| `deno run app.ts` | `deno` |

### 3.2 后续参数

后续参数中，若某 token 是文件路径（含 `/` 或 `\`），取其 basename；否则原样保留。

示例：

| 原始命令 | 规范化结果 |
|---|---|
| `C:\tools\python.exe .\train.py --epochs 10` | `python train.py --epochs 10` |
| `./python ./scripts/train.py --verbose` | `python train.py --verbose` |
| `node -e "console.log(1)"` | `node -e "console.log(1)"` |

### 3.3 规范化结果的用途

规范化后的字符串用于与黑白名单做前缀匹配，以及在确认弹窗中显示。

## 4. 匹配逻辑

固定三步判断，无模式切换：

```
原始命令 → 规范化 → 黑名单前缀匹配 → 命中 → 拒绝（静默）
                             ↓ 不命中
                       白名单前缀匹配 → 命中 → 允许（静默）
                             ↓ 不命中
                       广播确认请求到所有前端 → 等待用户决定
```

### 4.1 黑名单匹配

对规范化后的命令字符串做前缀匹配。可包含多词参数。

| 黑名单条目 | 匹配的命令 | 不匹配的命令 |
|---|---|---|
| `python -c` | `python -c "os.system(...)"`、`./python -c "..."` | `python train.py` |
| `node -e` | `node -e "..."` | `node server.js` |
| `rm -rf` | `rm -rf /tmp/data`、`rm -rf *` | `rm file.txt` |
| `sudo` | `sudo anything` | `sudoku` |

命中黑名单后静默拒绝，不弹窗，不通知前端。

### 4.2 白名单匹配

同样的前缀匹配机制。条目长度由用户决定，不同长度表达不同信任粒度：

| 白名单条目 | 信任范围 |
|---|---|
| `python` | 信任所有 python 调用 |
| `python train.py` | 信任 train.py 脚本的所有调用 |
| `git` | 信任所有 git 命令 |

命中白名单后静默允许，不弹窗。

### 4.3 黑名单优先

当一个命令同时命中黑名单和白名单时，以黑名单为准，拒绝执行。例如白名单有 `python`，黑名单有 `python -c`，则 `python -c "..."` 被黑名单拦截。

## 5. 确认弹窗

### 5.1 弹窗布局

当命令既未命中黑名单也未命中白名单时，弹出确认对话框：

```
┌──────────────────────────────────────────────┐
│  命令执行确认                             [×] │
│──────────────────────────────────────────────│
│                                              │
│  「{智能体名称}」请求执行：                     │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │ 原始: > {完整原始命令}                   │  │
│  │ 规范: > {规范化后的命令}                 │  │
│  │ 目录:  {工作目录}                       │  │
│  └────────────────────────────────────────┘  │
│                                              │
│  [  允许  ]    [  拒绝  ]                     │
│                                              │
│  ☐ 不再询问，匹配: {规范化命令前缀}      [✎] │
│     允许 → 入白名单 / 拒绝 → 入黑名单         │
│                                              │
└──────────────────────────────────────────────┘
```

### 5.2 元素说明

| 元素 | 作用 |
|---|---|
| 智能体名称 | 让用户判断该 agent 执行此命令是否合理 |
| 原始命令 | 用户看到实际执行的完整命令以判断安全性 |
| 规范命令 | 展示匹配基准，同时也是默认写入名单的值 |
| 工作目录 | 命令的执行上下文影响风险评估 |
| 允许 / 拒绝 | 核心决策 |
| ☐ 不再询问 | 勾选后，允许 = 规范化前缀加入白名单；拒绝 = 加入黑名单 |
| [✎] | 点击后可编辑将要写入名单的条目，例如将 `python train.py` 改为 `python` |
| [×] | 关闭对话框，等同于拒绝 |

### 5.3 弹窗中的自动提取

「不再询问」默认填写的内容为规范化命令的**解释器名 + 紧接着一个非参数部分**。提取方法是：跳过以 `-` 或 `--` 开头的 token。例如 `python train.py --epochs 10` 提取为 `python train.py`。用户可通过 [✎] 修改。

## 6. 多浏览器 / 多标签页

用户可能同时打开多个浏览器标签页或窗口，连接同一个后端。确认弹窗需要正确应对这种场景。

### 6.1 所有页面同时弹出

当一个命令需要确认时，所有已打开的前端页面都应弹出确认对话框，不应只在某一个页面上显示。这样用户在哪个页面上都能看到并处理，不需要切换标签页。

### 6.2 同一条命令只弹一次

每个前端页面收到确认请求后，需要记住已处理过的请求。同一条命令在一个页面上不应重复弹出两次。

### 6.3 一人决定即可

多个页面同时弹出同一命令的确认对话框后，用户只要在任意一个页面上做出决定（允许或拒绝），该决定即生效。其他页面上同一条命令的对话框应自动关闭，不应再要求用户处理第二次。

### 6.4 后续操作忽略

当用户在页面 A 上已经操作了某条确认请求后，再在页面 B 上尝试操作同一条请求，页面 B 的操作应被忽略。不应出现"页面 A 允许了但页面 B 又拒绝了导致结果矛盾"的情况。

### 6.5 新打开的页面不显示已处理的命令

用户处理了一条确认请求后，如果之后又打开了新的标签页或浏览器窗口，新页面不应再弹出已处理过的确认请求。

---

## 7. 无前端连接

### 7.1 不超时、不自动拒绝

确认请求发出时若没有任何前端页面连接，不应超时自动拒绝，也不应静默放过。命令应暂停等待，直到用户连接上前端并做出决定。

### 7.2 连接后恢复

用户关闭所有浏览器后重新打开，之前等待中的确认请求应正常弹出。用户不应因为暂时断连而丢失对命令的控制权。

### 7.3 不丢失决策权

无论是否断连，不存在命令因无人确认而被静默放过或静默拒绝的情况。每条命令最终都必须经过用户决策。

## 8. 系统提示词注入

AI 应当知晓当前的审核策略，以便预期确认机制的存在、不在被拒绝后反复重试。提示词中需包含以下信息：

```
【命令执行安全策略】
白名单: {白名单条目}
黑名单: {黑名单条目}
不在名单中的命令执行前需要用户确认，用户未响应前请耐心等待。
如果收到 confirmed=false，说明用户拒绝了此次命令执行，不要重试。
```

## 9. 设置界面

### 9.1 入口

设置界面应能从设置页的模块设置 > localcmd 卡片中进入「命令审核」设置。

### 9.2 组织列表视图

进入后显示所有组织的审核策略概览：

```
┌──────────────────────────────────────────────────┐
│  命令审核设置                                     │
│──────────────────────────────────────────────────│
│                                                  │
│  默认策略（新建组织时使用）                         │
│  ┌──────────────────────────────────────────┐    │
│  │ 白名单: 空                                │    │
│  │ 黑名单: [rm -rf] [sudo] [del /f]        │    │
│  │        [python -c] [node -e] [bash -c]  │    │
│  │        [cmd /c] [powershell -Command]   │    │
│  └──────────────────────────────────────────┘    │
│  [ 编辑默认值 ]                                  │
│                                                  │
│  各组织策略                                       │
│  ┌──────────────────────────────────────────┐    │
│  │ 组织: 默认组织                   [ 编辑 ] │    │
│  │ 白名单: [python train.py] [git] [ls]     │    │
│  │ 黑名单: [rm -rf] [sudo] [python -c]      │    │
│  │                    (共 3 条)              │    │
│  └──────────────────────────────────────────┘    │
│  ┌──────────────────────────────────────────┐    │
│  │ 组织: 测试环境                   [ 编辑 ] │    │
│  │ 白名单: 空                        (未配置) │    │
│  │ 黑名单: 空                        (未配置) │    │
│  │ 注: 未配置时使用默认策略                   │    │
│  └──────────────────────────────────────────┘    │
│                                                  │
└──────────────────────────────────────────────────┘
```

- 每个组织显示其当前白名单和黑名单条目
- 未单独配置策略的组织使用默认策略，并标明"未配置，使用默认策略"
- 点击「编辑」进入该组织的策略编辑视图

### 9.3 单个组织的策略编辑视图

点击某个组织的「编辑」或「编辑默认值」后，进入该组织的编辑视图：

```
┌──────────────────────────────────────────────────┐
│  命令审核 › 默认组织                               │
│──────────────────────────────────────────────────│
│                                                  │
│  匹配规则：                                       │
│  - 命令执行前先规范化（去路径、去 .exe/.bat 后缀） │
│  - 用规范化结果做前缀匹配，条目越长越精确           │
│  - 黑名单优先级高于白名单                         │
│  - 例: "python train.py" 可匹配完整路径下的调用    │
│                                                  │
│  白名单     自动允许的命令                         │
│  ┌──────────────────────────────────────────┐    │
│  │ [python train.py] [git] [ls]    [+ 添加]  │    │
│  └──────────────────────────────────────────┘    │
│                                                  │
│  黑名单     自动拒绝的命令                         │
│  ┌──────────────────────────────────────────┐    │
│  │ [rm -rf] [sudo] [python -c]     [+ 添加]  │    │
│  └──────────────────────────────────────────┘    │
│                                                  │
│  [ 恢复默认值 ]                                  │
│                                                  │
└──────────────────────────────────────────────────┘
```

### 9.4 编辑交互

- 点击「+ 添加」出现输入框，输入后回车确认
- 点击标签 × 删除
- 「恢复默认值」将当前组织策略清空，恢复为使用默认策略。需要二次确认

### 9.5 生效

修改后立即生效，下一次命令调用时按新规则判断。

## 10. 默认值

```
白名单: 空
黑名单: rm -rf, sudo, del /f, python -c, node -e, bash -c, cmd /c, powershell -Command
```

白名单默认为空——用户自行决定信任哪些命令。黑名单覆盖最高频的危险解释器内联执行模式。

## 11. 组织间隔离

审核策略归属于创建它的组织。不同组织的策略互相独立，互不影响。组织删除后，其策略随之清除。
